# 大小筛选对照实验计划

## 范围与问题

本实验属于第五阶段的验证与交付，不扩展网页或文件操作功能，不接入 C++。回答：在给定测试数据中，先按大小筛选能减少多少哈希文件与字节读取，是否影响重复判定，热缓存条件下耗时有什么变化？

不扫描真实课件，不写业务数据库，不隔离或删除用户文件。实验脚本只在项目 `benchmark_data/` 下生成专用数据；结果保存到 `docs/experiments/`。

## 两个方案与公平比较

- 全量哈希：所有生成的普通文件计算 SHA-256。
- 大小筛选：只为大小组中至少有两个文件的成员计算 SHA-256。

共用一套元数据读取、属性检查、哈希分组和实际内容确认代码；调用项目已有 `calculate_hash`、`files_equal`、属性检查函数。唯一差异是是否跳过唯一大小组。本实验测检测管线，不测网页、数据库和隔离，也不将结果直接称为完整应用加速。

不是给生产扫描器新增模式。使用固定随机种子和静态普通文件，无硬链接、符号链接或并发修改；这些边界已由功能测试分别验证。

## 三种受控场景

每场景 60 个文件，约数 MiB，保持小规模可复现：

1. 大小大多不同：54 个唯一大小文件、两组各 3 份副本，预期 2 组重复。
2. 大小相同但内容不同：60 个同大小、不同内容文件，预期 0 组重复；两方案应计算相同数量哈希。
3. 真实副本较多：10 组，每组 6 份相同内容，预期 10 组重复；两方案应计算相同数量哈希。

生成内容后用内容 SHA-256 建立独立预期成员清单；检测结果逐组比较相对路径，不只比较组数。

## 测量流程

1. 核对工作区、记录 Python、系统、脚本和核心模块版本摘要。
2. 用排他创建方式生成专用数据；已有数据不得覆盖，重复运行复用并校验原始清单。
3. 两方案各预热一次；正式运行各 7 次，每轮交替先后顺序。
4. 每次验证文件数、字节数、哈希数、哈希字节数与重复成员清单。
5. 保存逐次 CSV、结构化 JSON 与 Markdown 摘要；报告中位数、最小值与最大值。
6. 加速比使用“全量耗时中位数 / 筛选耗时中位数”；不挑最好单次，不保证所有场景变快。

## 解释限制与验收

生成数据、预热与重复读取会影响系统缓存，因此只报告本机热缓存测量。无清空缓存、峰值内存、冷启动或多机器结论。不把哈希输入字节数当成设备实际 I/O（内容确认还会读文件）。

所有运行必须与预期成员完全一致，哈希量符合场景设计。输出包含环境、数据规模、原始数值、限制和重跑命令。未实际运行的 Linux 实验不得标为完成。

学习节奏：先共同搭实验框架；用户解释为什么同大小场景不能省哈希，并运行复现实验；随后尝试独立调整一项数据参数。实验完成后只整理证据与提交，不顺势追加小功能。
