# FileScope 项目框架说明

## 当前做到了什么

已跑通本机上的完整流程：扫描测试文件，保存 SQLite，网页查看历史和重复报告，主动隔离副本，再恢复到原路径。当前是本地学习与演示版本，不是可直接开放到公网的生产服务。

## 各部分负责什么

| 文件或目录 | 职责 |
| --- | --- |
| `app.py` | Flask 网页入口：接收请求、调用业务函数、返回页面或跳转 |
| `src/services.py` | 组织扫描流程：校验目录 → 扫描 → 保存 → 返回扫描编号 |
| `src/filescope.py` | 文件扫描、大小分组、哈希与内容确认；也保留命令行入口 |
| `src/database.py` | 执行 SQL，保存扫描记录、查询历史与文件数据 |
| `schema.sql` | 定义表结构，不存放实际扫描数据 |
| `filescope.db` | SQLite 实际数据文件，由程序创建，不提交 Git |
| `src/reports.py` | 将数据库查询结果整理成重复分组和理论空间统计 |
| `src/quarantine.py` | 操作前重新检查、隔离与恢复文件、记录操作状态 |
| `templates/` | Jinja HTML 模板：决定网页显示什么、如何排版 |
| `quarantine/` | 隔离文件的实际存放位置，不提交 Git |
| `tests/` | 自动验证扫描、网页流程与隔离恢复等行为 |

这是逐步整理的结构：扫描器仍有命令行入口，数据库模块仍保留终端显示函数。它不是每一层都完全拆开的最终架构，也暂时不为拆文件而大规模重构。

## 三条关键数据流

### 发起扫描

```text
网页表单 → app.py → services.scan_and_save
                       ├─ filescope.scan_directory → 文件记录
                       └─ database.save_scan_results → SQLite → 扫描编号
扫描编号 → 网页跳转到详情
```

命令行扫描也调用同一个服务函数，所以没有为网页重新写一套扫描器。文件内容由 Python 从磁盘读取，不上传到外部服务。

### 查看报告

```text
浏览器请求详情 → app.py → database 查询 SQLite
                       → reports 整理重复分组
                       → render_template 填入 HTML 模板
                       → 浏览器显示页面
```

网页不直接连接数据库。Python 查询数据，Jinja 把数据填进模板，浏览器收到生成的 HTML。查看旧报告不会重新扫描，它显示的是当时保存的快照。

### 隔离与恢复

```text
网页按钮 → app.py → quarantine.py
                     ├─ 查询记录并重新验证当前文件
                     ├─ 在原路径与隔离路径之间移动文件
                     └─ SQLite 记录原路径、隔离路径和操作状态
```

数据库不是文件本体。隔离文件存在磁盘的 `quarantine/` 中，数据库记住它的位置。文件操作和数据库更新不能自动作为一个整体成功或失败，因此实现了操作意图记录和失败后的补偿尝试；异常中断仍可能需要人工核对。

## 借鉴经典项目的位置

- dupeGuru：借鉴检测核心与展示分离、重复组中区分保留文件和副本的思路。

- SQLite 历史、Flask 页面、隔离恢复是 FileScope 的扩展，不宣称是原项目功能的逐项复现，也未把它们的代码整体搬进来。

版本和源码阅读记录见项目外的 `FileScope-开源项目对照.md`。借鉴的是可说明的设计和流程，不是为了堆功能或推翻现有实现。

## 学习与下一阶段

当前优先能解释三件事：入口接收到什么，调用了哪个模块，结果保存在哪里或返回给谁。不要求背下整份代码。

接下来先验证 Linux 环境中的安装、测试和本机运行，再完善演示与交付说明。跨平台验证前不宣称已经支持 Linux。暂不增加永久删除、登录系统、独立前端框架或任务队列。

安全边界：只使用测试数据；隔离不释放磁盘空间；目前仅支持同一文件系统且支持硬链接的普通文件；恢复不覆盖同名文件；检查不是文件锁，操作时不要用其他程序同时编辑文件。
